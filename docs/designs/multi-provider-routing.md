# Design: Multi-provider upstream with invisible quality-then-cost routing

Generated by /office-hours on 2026-06-02
Repo: olaDmenace/veridigits
Status: APPROVED (direction) — implementation not started
Mode: Builder

## Problem

Today all numbers come from 5SIM. We want more upstream supply and better success
rates — especially for **strict-screening services (WhatsApp, Google)** where a cheap
VoIP number often never receives the code. SMSPool is stubbed; TextVerified is a strong
option for high-success WhatsApp/Google (US-centric, pricier).

## Decision

**Invisible auto-routing.** The buy flow stays a single "get a number" action — the user
never picks a provider. Selection is automatic and per-service:

- Strict-screening services (WhatsApp, Google, ...) → prefer the high-success provider
  (TextVerified) first.
- Everything else → cheapest *reliable* provider (5SIM / SMSPool).
- **Hard fallback to 5SIM** on out-of-stock / API error, every time.

Ranking signal order: **preference/tier → recent success rate → price**, then fallback.
This reuses the operator success-rate scoring already in the codebase
(`pickBestCandidate`, `recent_received_count/recent_total_count`,
`operator_success_rate_tracking`).

Real upstream names are **never** exposed to users (hard constraint).

## Premises (agreed)

1. "Set an alternative as the global *primary*, 5SIM as global *fallback*" is the wrong
   frame — providers differ **per service**, not in general. Route per service instead. ✓
2. The #1 churn driver is a number that never receives the SMS → optimize **success
   rate**, not provider identity. ✓
3. White-labeling is mandatory regardless of whether choice is ever surfaced. ✓
4. User-facing provider choice, if ever added, should be **named value tiers**
   ("Standard" / "Premium — best for WhatsApp"), not opaque "Server 1–N" (which causes
   decision fatigue and advertises that some servers are worse). Deferred (see Roadmap).

## Approaches considered

- **A — Invisible auto-routing (CHOSEN).** Backend-only; no buy-flow UI change.
- **B — Named quality tiers.** Surface "Standard/Premium" with per-tier pricing. The
  monetization follow-up. Deferred.
- **C — Opaque "Veridigits Server 1–N" picker.** Rejected as primary UX — weakest value
  story, trust risk, most UI.

## Implementation shape (for the eng plan, not built yet)

1. **SMSPool provider** — implement the stub in `lib/providers/smspool.ts` against the
   SMSPool API (getPriceAndAvailability, buyActivation, checkOrder, cancelOrder,
   syncCatalog; rental optional). Mirror the `5sim.ts` structure + error mapping
   (`ProviderOutOfStockError` / `ProviderApiError`).
2. **TextVerified provider** — new `lib/providers/textverified.ts` + register in
   `lib/providers/index.ts` (env `TEXTVERIFIED_API_KEY`). Note its model differs
   (US numbers, bearer-token auth, verification "targets"/reservations) — confirm
   against their API before mapping to the `OtpProvider` interface.
3. **Routing preference** — add a per-(service[,country]) provider preference. Options:
   a small `provider_preferences` table or extend `provider_services` with a
   `tier`/`preference_rank`. Keep it data-driven (admin-editable), like `pricing_rules`.
4. **Registry** — update `buyCheapestActivation` (and the `getQuote` candidate ranking)
   to sort by `preference_rank → success_rate → price`, preserving the existing
   try-next-on-failure fallback (still capped at `MAX_FALLBACK_TRIES`).
5. **Catalog sync** — extend `sync-catalog` Inngest job to pull SMSPool + TextVerified
   catalogs into `provider_services`.
6. **Admin** — surface the new providers in `/admin/providers` (enable/disable, see
   success rates) using white-labeled display names.

## Open questions (need answers before/while building)

- TextVerified: US-only? activation vs rental model? exact endpoints + auth? (verify via
  their API docs — https://www.textverified.com/ ).
- How are "strict-screening" services flagged — a column on `services`, or a hardcoded
  set, or derived from the preference table? (Lean: the preference table.)
- Do we want a per-service *price ceiling* so a premium provider never silently 3x's the
  user's cost vs 5SIM? (Probably yes — a sanity guardrail.)

## Dependencies (owner action)

- **API keys:** `SMSPOOL_API_KEY` and `TEXTVERIFIED_API_KEY` (real accounts with balance
  to test live). Add to `.env.local` (never committed).
- Decide the initial service→provider preference map (e.g. WhatsApp/Google → TextVerified;
  rest → cheapest reliable).

## Roadmap

2. **Next:** Approach B — named quality tiers + per-tier pricing (monetization), once A is
   proven and we see real success-rate deltas.
